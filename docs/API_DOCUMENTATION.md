# Документація Kindergarten API

**Дата:** 11.11.2026
**Версія API:** 1.0.0
**Стек:** Node.js ≥ 22.13, Express 5, SQLite (`better-sqlite3`), Zod, JWT, bcryptjs
**Джерело істини:** `index.js` (уся серверна логіка в одному файлі). Вимоги замовника: `README.md`. Критерії приймання: `ACCEPTANCE_CRITERIA.md`.

---

## 1. Загальні відомості

REST API для управління приватним дитячим садком: діти, батьки та опікуни, персонал, групи, кімнати, дисципліни, розклад, рахунки, прибуток, прогноз і журнал змін даних.

- Формат обміну: JSON (`Content-Type: application/json`).
- Назви полів: `camelCase` і в JSON, і в колонках БД.
- Дати: `YYYY-MM-DD`, час: `HH:MM`.
- Гроші: цілі гривні, без копійок.
- Усі повідомлення про помилки українською.

### 1.1. Формат помилки

```json
{ "error": "опис помилки" }
```

| Код | Значення |
|---|---|
| 200 | OK |
| 201 | Створено |
| 204 | Видалено, тіло порожнє |
| 400 | Некоректні дані (валідація Zod, формат ID, некоректний JSON) |
| 401 | Немає або недійсний токен |
| 403 | Токен дійсний, але прав недостатньо |
| 404 | Запис або маршрут не знайдено |
| 409 | Конфлікт бізнес-правил (зайнятість, пов'язані записи, дублікат) |
| 500 | Внутрішня помилка сервера |
| 503 | База даних недоступна (`/health`) |

### 1.2. Валідація вхідних даних

- ID у шляху й query: рядок цифр без ведучого нуля й знака (`/rooms/01`, `/rooms/1.0`, `/rooms/+1` дають `400`).
- ID у тілі: додатне ціле JSON-число.
- Рядки обрізаються по краях; обов'язкові рядки не можуть бути порожніми.
- `POST`: невідомі поля дають `400` (виняток: `POST /rooms` і `PUT /children/:id/parents` ігнорують зайві поля).
- `PATCH`: усі поля необов'язкові, але хоча б одне має бути передане, інакше `400`.
- Порядок перевірок у більшості маршрутів: `401` → `403` (роль) → `400` (валідація) → `404` → `403/409` (бізнес-правила).

## 2. Запуск і конфігурація

```bash
npm ci            # залежності за package-lock.json
npm run setup     # створює .env з випадковими паролями (якщо .env немає)
npm run dev       # запуск з перезапуском при змінах
npm start         # звичайний запуск
npm test          # автотести (node:test) з папки test/
npm run lint      # ESLint
npm run format    # Prettier
npm run db:reset  # ВИДАЛЯЄ kindergarten.db (сервер зупинити!)
```

### 2.1. Змінні середовища (`.env`)

| Змінна | Обов'язкова | Опис |
|---|---|---|
| `PORT` | ні (3000) | Порт сервера |
| `ADMIN_PASSWORD` | так, ≥ 12 символів | Пароль користувача `admin`, створюється при першому запуску |
| `JWT_SECRET` | так, ≥ 32 символи | Секрет підпису JWT; без нього сервер не стартує |
| `DB_PATH` | ні (`kindergarten.db`) | Шлях до файлу БД (використовують автотести) |

Зміна `ADMIN_PASSWORD` не впливає на вже створеного адміна: потрібен `npm run db:reset`.

### 2.2. Що створюється при старті

- База SQLite у режимі WAL, `foreign_keys = ON`.
- 10 таблиць: `parents`, `employees`, `rooms`, `users`, `groups`, `children`, `child_parents`, `activities`, `schedule_slots`, `data_history`.
- Тригери: контроль місткості груп та історія змін для 9 таблиць.
- Міграція `groups.capacity` для старих баз.
- Seed: користувач `admin` і 5 дисциплін (Музика, Англійська, Фізкультура, Вільна боротьба, Шахи). Повторний запуск не дублює дані.

## 3. Автентифікація та ролі

### 3.1. Вхід

`POST /auth/login`

```json
{ "login": "admin", "password": "<пароль>" }
```

Відповідь `200`:

```json
{
  "token": "<JWT>",
  "tokenType": "Bearer",
  "expiresIn": 28800,
  "user": { "id": 1, "login": "admin", "role": "admin" }
}
```

JWT (HS256) містить `userId` і `role`, діє 8 годин. Усі інші запити (крім `/health`, `/api/health`, `/auth/login`) вимагають заголовок:

```
Authorization: Bearer <token>
```

Токен відхиляється (`401`), якщо: заголовка немає, формат не `Bearer <token>`, підпис або строк недійсний, користувача видалено або його роль змінилася.

### 3.2. Ролі

| Роль | Призначення |
|---|---|
| `admin` | Повний доступ, єдина роль з `DELETE`, фінансова звітність, історія змін |
| `manager` | Діти, батьки, групи, персонал, кімнати, дисципліни, розклад. Без `DELETE`, без фінзвітів, не встановлює `rent` |
| `parent` | Лише власні діти (основний представник або опікун), розклад групи дитини, `notes` своєї дитини |
| `teacher` | Власний розклад і групи, де веде заняття; перенос власних слотів. Дані дітей і батьків недоступні |

Вихователі й помічники не мають акаунтів, це записи в `employees` для розрахунку зарплат.

Зв'язок акаунта: `parent` потребує `parentId`, `teacher` потребує `employeeId`, `admin` і `manager` не мають жодного з них.

## 5. Опис ресурсів

### 5.1. Користувачі

**`POST /users`**

```json
{ "login": "parent1", "password": "Parent1-Pass-2026", "role": "parent", "parentId": 1 }
```

- `login`: без пробілів по краях, непорожній. `password`: від 12 символів.
- `role`: `admin`, `manager`, `parent`, `teacher`.
- `parent` потребує `parentId`; `teacher` потребує `employeeId`; для `admin`/`manager` зв'язки заборонені (`400`).
- Менеджер може створювати лише `parent`, інакше `403`.
- `404`, якщо батька або працівника не існує; `400`, якщо працівник не має посади `teacher`; `409`, якщо логін зайнятий.
- Відповідь `201`: `{ id, login, role, parentId, employeeId }`. Хеш пароля ніколи не повертається.

**`GET /users`** повертає масив `{ id, login, role, parentId, employeeId }`.

**`DELETE /users/:id`**: адміністратор не може видалити власний акаунт (`409`).

### 5.2. Батьки

Поля: `fullName` (обов'язкове), `phone`, `email`, `relationNote` (довідкова примітка, не впливає на пільги).

- `phone`: цифри, пробіли, дефіси, дужки, `+` на початку; від 10 до 15 цифр.
- `email`: валідний формат, до 254 символів.
- Порожній рядок або `null` для контакту зберігається як `NULL`; `PATCH` може очистити поле.
- `DELETE`: `409`, якщо є діти з цим основним батьком або акаунт.

### 5.3. Працівники

Поля: `fullName`, `position` (`manager`, `educator`, `assistant`, `teacher`), `salaryRate` (невід'ємне ціле або `null`, довідкове).

Правила (`409`):
- у садку може бути лише один менеджер;
- не можна змінити посаду працівника, який закріплений як вихователь або помічник групи, або як викладач (дисципліна, розклад, акаунт);
- `DELETE` заборонено, якщо працівник у групі, дисципліні, розкладі або має акаунт.

### 5.4. Кімнати

Поля: `name` (унікальна), `type` (`base` або `specialized`), `rent` (невід'ємне ціле, за замовчуванням 50 000).

- Менеджер із полем `rent` у `POST` або `PATCH` отримує `403`. Без `rent` менеджер створює й змінює кімнату нормально.
- Валідація тіла виконується перед перевіркою ролі, тому некоректний `rent` у менеджера може повернути `400` замість `403`.
- `409`: дубль назви; базова кімната групи не може стати `specialized`; зал дисципліни не може стати `base`; `DELETE` кімнати, що використовується групою, дисципліною або розкладом.

### 5.5. Дисципліни

Поля: `name` (унікальна), `teacherId`, `roomId` (обидва необов'язкові).

- Викладач має мати посаду `teacher` (`409` інакше, `404` якщо не існує).
- Кімната має бути `specialized` (`409` інакше, `404` якщо не існує).
- `DELETE`: `409`, якщо дисципліна є в розкладі.

### 5.6. Групи

Поля: `name` (унікальна), `ageCategory` (2–5), `capacity` (1–20, за замовчуванням 20), `roomId`, `educatorId`, `assistantId`.

Відповідь містить `enrolled` (кількість активних дітей). Батьки отримують лише `id`, `name`, `ageCategory`.

Видимість `GET /groups` і `GET /groups/:id`:

| Роль | Що бачить |
|---|---|
| admin, manager | усі групи |
| teacher | групи, де він вихователь, помічник або веде заняття |
| parent | групи своїх активних дітей; чужа група дає `404` |

Правила:
- максимум 30 груп (`409`);
- кімната: існує (`400`), тип `base` (`409`), не закріплена за іншою групою (`409`);
- вихователь має посаду `educator`, помічник `assistant` (`400`); один працівник не може бути закріплений за двома групами (`409`);
- вихователь і помічник не можуть збігатися (`400`);
- `capacity` не може бути меншою за поточну кількість дітей (`409`);
- зміна `ageCategory` неможлива, якщо в групі є діти іншого віку (`409`);
- `DELETE`: `409`, якщо є діти або розклад.

### 5.7. Діти

Поля: `fullName`, `birthDate`, `parentId` (основний представник і платник), `guardianIds` (до 9 додаткових опікунів), `groupId`, `discountPercent` (0, 10, 20, 30), `paymentPlan` (`monthly`, `yearly`), `notes`, `isActive`.

Відповідь містить `group: { id, name } | null` і `parents: [{ id, fullName, relationNote, isPrimary, phone, email }]`. Для ролі `parent` поля `phone` і `email` приховані.

Правила:
- вік від 2 до 5 повних років, дата не в майбутньому (`400`);
- зарахування в групу: вік дитини має дорівнювати `ageCategory` (`409`), місце має бути вільне (`409` «Група заповнена»);
- неактивна дитина не може бути призначена до групи (`400`);
- `isActive = false` автоматично відкріплює дитину від групи;
- `parentId` і `guardianIds` у `PATCH` змінювати не можна (`400` з підказкою про `PUT /children/:id/parents`);
- `guardianIds` без дублів і без `parentId`;
- `parent` у `PATCH` може змінювати лише `notes` (`403` для інших полів); чужа дитина дає `404`;
- викладач до `/children*` отримує `403`.

**`PUT /children/:id/parents`**: `{ "parentId": 1, "guardianIds": [2] }`, повна заміна представників у транзакції.

Фільтри `GET /children`: `groupId`, `isActive` (`0`, `1`, `true`, `false`).

### 5.8. Рахунок

`GET /children/:id/invoice`: розраховується на льоту.

```json
{
  "childId": 1, "fullName": "...", "paymentPlan": "monthly", "discountPercent": 0,
  "period": "month",
  "lines": [ { "name": "Навчання", "amount": 15000 }, { "name": "Харчування", "amount": 12000 } ],
  "total": 27000
}
```

- Доступ: `admin`, `manager`; `parent` лише основний представник (опікун отримує `403`, чужий батько `404`); `teacher` `403`.
- Неактивна дитина: `409`.
- Тариф харчування: за `group.ageCategory`, а без групи за повним віком на дату запиту.
- `monthly`: `period = "month"`, навчання за місяць + харчування за місяць. `yearly`: `period = "year"`, навчання за рік + харчування за 12 місяців.

### 5.9. Розклад

- **Сітка:** 6 слотів по 30 хв: `09:30`, `10:00`, `10:30`, `11:00`, `11:30`, `12:00`. `dayOfWeek`: 0 (пн) – 4 (пт), лише цілі числа.
- **`POST /schedules/generate`:** видаляє поточні слоти й будує нові. Групи сортуються за віком від старших, `activityIndex = (i + d) mod 5`, слоти від 09:30 за зростанням. Дисципліни беруться за `id` (перші 5). `409`, якщо дисциплін менше 5 або в якоїсь немає викладача чи кімнати.
- **`GET /groups/:id/schedule`:** admin, manager бачать будь-яку; `parent` лише групу своєї дитини (`403` інакше); `teacher` лише групи, де веде заняття (`403` інакше). `404`, якщо групи або розкладу немає.
- **`GET /teachers/:id/schedule`:** `parent` `403`; `teacher` лише власний (`403`).
- **`PATCH /schedules/:id`:** тіло `{ "startTime": "10:00", "dayOfWeek": 1 }`, обидва поля обов'язкові. Порядок: слот існує (`404`) → тіло (`400`) → власник слота для викладача (`403`) → колізії (`409`).

Колізії (`409`):
- група вже має інше заняття цього дня: `type: "group_limit"`;
- збіг часу для групи, викладача або кімнати: `type` = `group_busy`, `teacher_busy`, `room_busy`;
- у кожному `409` є `slotId` конфліктного слота.

### 5.10. Фінанси

**Константи (`CONFIG`):** навчання 15 000/міс; знижка плану `yearly` 12%; пільги 0, 10, 20, 30%; оренда 50 000 за кімнату; менеджер 80 000; викладач 40 000; 20 робочих днів на місяць.

**Навчання:** `річна база = 180 000 × (100 − пільга) / 100`; для `yearly` додатково `× 88 / 100`. У прибутку береться місячний еквівалент (`річна сума / 12`).

| Пільга | monthly, грн/міс | yearly, грн/рік | yearly, екв. грн/міс |
|---|---:|---:|---:|
| 0% | 15 000 | 158 400 | 13 200 |
| 10% | 13 500 | 142 560 | 11 880 |
| 20% | 12 000 | 126 720 | 10 560 |
| 30% | 10 500 | 110 880 | 9 240 |

**Харчування** (поза прибутком, без пільг): 2 р. 300, 3 р. 400, 4 р. 500, 5 р. 600 грн/день; місяць = день × 20.

**Зарплати:**
- вихователь: `2 000 × min(n, 12) + 5 000 × max(0, n − 12)`;
- помічник: `20 000 + 3 000 × max(0, n − 12)`;
- `n` це кількість активних дітей групи (0–20).

**`GET /groups/:id/profit`:** `{ groupName, childrenCount, income, expenses, netProfit }`. Витрати = 50 000 + вихователь + помічник. Контроль: 12 п'ятирічок без пільг, `monthly` дають `netProfit = 86 000`.

**`GET /admin/profit`:** `{ totalIncome, totalExpenses, totalNetProfit }`. Витрати = `SUM(rooms.rent)` + 80 000 + 40 000 × кількість викладачів + зарплати вихователів і помічників усіх груп.

### 5.11. Прогноз (бонус)

`GET /admin/forecast?children=150&age=5&groupSize=20&discountPercent=0&paymentPlan=monthly`

| Параметр | Обов'язковий | Діапазон | За замовчуванням |
|---|---|---|---|
| `children` | так | 1–600 | |
| `age` | ні | 2–5 | 5 |
| `groupSize` | ні | 1–20 | 20 |
| `discountPercent` | ні | 0, 10, 20, 30 | 0 |
| `paymentPlan` | ні | `monthly`, `yearly` | `monthly` |

Припущення: діти розподіляються по групах рівномірно; на групу одна базова кімната, вихователь і помічник; на дисципліну один викладач і один зал; дохід лише від навчання. Якщо потрібно понад 30 груп, відповідь `400`.

Відповідь: `input`, `groups { count, minSize, maxSize }`, `teachers`, `rooms { base, specialized, total }`, `income`, `expenses { rent, manager, teachers, educators, assistants, total }`, `netProfit`, `breakEvenChildren`, `comparison` (групи по 12 і по 20). Контроль: 150 дітей по 20 дають 8 груп (6 по 19 і 2 по 18).

### 5.12. Журнал змін

Записи створюють лише тригери SQLite; через API таблиця `data_history` не змінюється.

**`GET /history`:** фільтри `tableName`, `recordId`, `action` (`INSERT`, `UPDATE`, `DELETE`), `limit` (1–100, 50), `offset` (≥ 0). Сортування від новіших. **`GET /history/:id`:** одна подія.

Запис: `{ id, tableName, recordId, action, oldData, newData, changedAt }`.

- Ведеться для: `users`, `parents`, `employees`, `rooms`, `groups`, `children`, `child_parents`, `activities`, `schedule_slots`.
- `recordId` текстовий; для `child_parents` формат `childId:parentId`.
- `UPDATE` без фактичних змін не записується; невдала операція (400, 404, 409) запису не залишає.
- Для `users` хеш пароля ніколи не зберігається й не повертається.

## 8. Обмеження та відомі особливості

- Увесь код в одному файлі `index.js` (вимога замовника).
- Перевірка зайнятості розкладу порівнює стартові моменти на 30-хвилинній сітці, а не довільні інтервали.
- У `POST /rooms` і `PATCH /rooms/:id` валідація тіла передує перевірці ролі.
- Редагування тарифів через API (`PATCH /settings`) не реалізовано (бонус).
- Таблиці рахунків і платежів немає: рахунок завжди обчислюється за поточними даними.
- Не зберігайте `.env`, паролі, JWT і `kindergarten.db` у Git.
