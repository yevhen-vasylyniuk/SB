# Технічне завдання: Сервер управління приватним дитячим садком (Backend RESTful API)

## 1. Загальні технічні вимоги та архітектура
- **Тип додатку:** Серверна частина (Backend RESTful API). Клієнтської частини (фронтенду) немає.
- **Формат обміну даними:** JSON (заголовок `Content-Type: application/json`).
- **Стек технологій:** Node.js + Express.
- **База даних:** SQLite через пакет `better-sqlite3`, файл БД — `kindergarten.db` (це лише сховище даних; уся робота з ним виконується в коді `index.js`).
- **Специфічне обмеження (Головний дебаф):** Уся серверна логіка, включаючи підключення до бази даних, створення таблиць (`CREATE TABLE IF NOT EXISTS`), заповнення початковими даними (seed) та всі SQL-запити, реалізуються **суворо в одному файлі `index.js`**. Створювати окремі файли для бази даних чи моделей (`db.js`, `database.js`, `schema.sql`) **заборонено** (підтверджено викладачем).
- **Автентифікація:** JWT (JSON Web Token). У payload токена зашиваються `userId` та `role`. Кожен захищений запит перевіряє валідність токена (`401 Unauthorized`) та права ролі (`403 Forbidden`).
- **HTTP-методи та статуси:** `GET`, `POST`, `PATCH`/`PUT`, `DELETE`. Коди відповідей: `200`, `201`, `204`, `400`, `401`, `403`, `404`, `409`.
- **Формат помилки:** `{ "error": "опис" }` з відповідним статус-кодом.

## 2. Рольова модель та права доступу
Система має 4 ролі користувачів (`admin`, `manager`, `parent`, `teacher`).
*Примітка:* Вихователі та помічники — це облікові сутності в базі даних для розрахунків, вони не мають власних логінів для входу в систему.

1. **Адміністратор (`admin` / "Дід"):**
   - Повний CRUD для всіх сутностей (тільки адмін має право на видалення через `DELETE`).
   - Призначає та змінює персональні пільги (0%, 10%, 20%, 30%).
   - Змінює тарифи, ставки зарплат персоналу та вартість оренди приміщень.
   - Має ексклюзивний доступ до загальної фінансової звітності (чистий прибуток садка та прибуток груп).

2. **Менеджер (`manager`):**
   - Створює та редагує картки дітей, батьків, груп, закріплює персонал.
   - Призначає та змінює персональні пільги дітям (0%, 10%, 20%, 30%) так само, як і адмін.
   - Перемикає статус дитини `isActive` через `PATCH /children/:id`.
   - Складає та редагує розклад занять.
   - Не має права видаляти сутності (`DELETE`), не може переглядати чистий прибуток садка та змінювати базові ставки зарплат/оренди.

3. **Батьки (`parent`):**
   - Бачать виключно свою дитину, свій рахунок (без доступу до чужих знижок) та розклад групи своєї дитини.
   - Можуть редагувати поле приміток (`notes`: алергії, особливості харчування) тільки для своєї дитини.

4. **Викладач (`teacher`):**
   - Бачить розклад своїх занять та розклад закріплених за ним груп.
   - Може змінювати слоти виключно власних занять за умови, що це не створює колізій (інакше отримує `409 Conflict`).

### Зв'язок акаунта з сутностями
У таблиці `users` є зовнішні ключі `parentId` (може бути `NULL`) та `employeeId` (може бути `NULL`):
- Для ролі `parent` поле `parentId` обов'язкове. Батько бачить лише картки дітей, де `child.parentId === user.parentId`.
- Для ролі `teacher` поле `employeeId` обов'язкове. Викладач переглядає та редагує лише слоти, де `slot.teacherId === user.employeeId`.
- **Створення акаунтів:** `POST /users` (тіло: `login`, `password`, `role`, `parentId` або `employeeId`). `admin` створює акаунти будь-якої ролі; `manager` може створювати лише акаунти ролі `parent`. Логін унікальний, інакше `409`. Видаляє акаунти лише `admin`.

## 3. Бізнес-логіка та валідації сутностей

- **Дитина (`Child`):**
  - Зв'язки: `parentId` (обов'язковий, посилання на батька), `groupId` (може бути `NULL`, якщо дитина ще не розподілена або неактивна).
  - Дата народження (`birthDate`); вік обчислюється з неї. Вік строго від 2 до 5 років включно (перевіряється на дату зарахування).
  - Пільга (`discountPercent`): 0%, 10%, 20%, 30% (встановлюється вручну адміном або менеджером). Категорія зв'язку батьків («родич», «депутат», «знайомий») — лише довідкова примітка і на пільгу не впливає.
  - План оплати (`paymentPlan`): `monthly` або `yearly`.
  - Примітки (`notes`): текстовий рядок про харчування та алергії (без складної системи дієт).
  - Активність (`isActive`, `INTEGER`, за замовчуванням `1`): якщо дитина вибула або не відвідує заклад, менеджер встановлює `isActive = 0` через `PATCH /children/:id`. Тоді дитина автоматично відкріплюється від групи (`groupId = NULL`), але лишається в базі з усіма даними. Неактивна дитина не враховується в місткості групи, зарплатах вихователя й помічника, прибутку (`WHERE isActive = 1`) та не отримує рахунок. Повернення: `isActive = 1` і нове призначення групи (діють звичайні перевірки віку групи та максимуму 20 дітей).
- **Група (`Group`):**
  - `ageCategory` (ціле `2`, `3`, `4` або `5`, обов'язкове): вікова категорія групи. Дитину можна зарахувати, лише якщо її повний вік на дату зарахування дорівнює `group.ageCategory`.
  - Формується виключно з дітей однакового повного віку (змішування вікових категорій суворо заборонено).
  - Місткість: від 1 до 20 дітей (жорсткий максимум).
  - Загальний ліміт садка: не більше 30 груп сумарно.
  - Закріплені ресурси: 1 базова кімната, 1 вихователь, 1 помічник вихователя.
- **Персонал та Кімнати:**
  - Дисципліни: музика, англійська, фізкультура, вільна боротьба, шахи. За кожною закріплений профільний викладач і спеціалізований зал.
  - Кімнати: Базові (закріплені за групами для постійного перебування та тихого часу) та спеціалізовані зали (під конкретні дисципліни).
- **Користувач (`User`):** `login`, `passwordHash`, `role`, `parentId`, `employeeId` (див. розділ 2).

## 4. Фінансова модель (Рахунки та Прибуток)

### Доходи від навчання
- **Базова вартість:** 15 000 грн/місяць (180 000 грн/рік).
- **Послідовний розрахунок знижок:**
  1. Спочатку від річної базової суми віднімається персональна пільга:
     $$\text{Сума після пільги} = 180\,000 \times (1 - p)$$
  2. Якщо обрано план `yearly`, від отриманої суми віднімається річна знижка 12%:
     $$\text{Підсумкова річна сума навчання} = \text{Сума після пільги} \times (1 - 0.12) = 180\,000 \times (1 - p) \times (1 - 0.12)$$

| Пільга | `monthly`, грн/міс | `yearly`, грн/рік | `yearly`, еквівалент грн/міс |
| --- | --- | --- | --- |
| 0% | 15 000 | 158 400 | 13 200 |
| 10% | 13 500 | 142 560 | 11 880 |
| 20% | 12 000 | 126 720 | 10 560 |
| 30% | 10 500 | 110 880 | 9 240 |

- У розрахунку щомісячного прибутку дохід кожної активної дитини береться як місячний еквівалент: місячна плата за планом `monthly` або 1/12 від підсумкової річної суми навчання за планом `yearly`.
- **Рахунки та дохід:** ендпойнт `GET /children/:id/invoice` розраховує суму **на льоту** за поточними даними дитини. Загальний дохід садка у звітах про прибуток формується на основі поточних тарифів, планів оплати та пільг активних дітей (`WHERE isActive = 1`). Окремої таблиці рахунків (`invoices`), збереження історичних станів, банківських платежів і сторонніх платіжних систем немає.

### Харчування (Транзитне)
- Оплачується окремо від навчання, у розрахунок чистого прибутку садка **не входить** (собівартість дорівнює закупівлі, маржі немає), пільги на їжу не діють.
- Денні тарифи за віком:
  - 2 роки — 300 грн/день;
  - 3 роки — 400 грн/день;
  - 4 роки — 500 грн/день;
  - 5 років — 600 грн/день.
- Місячний розрахунок: денний тариф × 20 робочих днів.
- **Правило визначення тарифу:** тариф харчування розраховується на льоту на дату запиту рахунку. Якщо дитина закріплена за групою, береться `group.ageCategory`; якщо дитина ще без групи, береться повний вік за `birthDate` на дату запиту.

### Рахунок для батьків (`GET /children/:id/invoice`)
Рахунок генерується динамічно і містить окремі рядки «Навчання», «Харчування» та загальний «Підсумок». Для неактивної дитини ендпойнт повертає `409 Conflict`.

- Якщо `paymentPlan === 'monthly'`:
  $$\text{Підсумок} = \text{Місячне навчання після пільги} + (\text{Денний тариф} \times 20)$$
- Якщо `paymentPlan === 'yearly'` (навчання за рік після обох знижок + харчування за 12 місяців без знижок):
  $$\text{Підсумок} = \text{Підсумкова річна сума навчання} + (\text{Денний тариф} \times 20 \times 12)$$

### Витрати та Чистий прибуток
- **Оренда:** 50 000 грн/міс за кожен запис у таблиці `rooms` (базові кімнати та спеціалізовані зали), незалежно від того, скільки годин вони використовуються:
  $$\text{Оренда} = 50\,000 \times \text{кількість записів у rooms}$$
- **Зарплатний фонд** = 80 000 (менеджер) + 40 000 × кількість викладачів дисциплін у таблиці `employees` + зарплати вихователів і помічників усіх груп за формулами нижче:
  - Менеджер: фіксовано 80 000 грн/міс.
  - Викладач дисципліни: 40 000 грн/міс за ставку.
  - Помічник вихователя: базова ставка 20 000 грн/міс. За кожну дитину в групі з 13-ї по 20-ту включно — доплата +3 000 грн за дитину.
  - Вихователь: 2 000 грн за кожну дитину з 1-ї по 12-ту; за кожну дитину з 13-ї по 20-ту включно — 5 000 грн за дитину замість 2 000 грн.
  - Приклад для 15 дітей: вихователь 12 × 2 000 + 3 × 5 000 = 39 000 грн; помічник 20 000 + 3 × 3 000 = 29 000 грн. Для 20 дітей: вихователь 64 000 грн, помічник 44 000 грн.
- **Чистий прибуток садка** = $\sum \text{Доходи від навчання (активні діти)} - (\text{Оренда всіх кімнат} + \text{Зарплатний фонд})$.
- **Прибуток групи** = дохід її активних дітей − (50 000 + зарплата вихователя + зарплата помічника). Він не містить загальних витрат (менеджер, викладачі, спеціалізовані зали).

## 5. Розклад (Schedule)

### Розпорядок дня (08:30–16:30)
| Час | Що відбувається |
| --- | --- |
| 08:30–09:00 | Сніданок (30 хв) |
| 09:00–09:30 | Вільний час |
| 09:30–12:30 | Навчальні заняття (6 слотів по 30 хв) |
| 12:30–13:00 | Обід (30 хв) |
| 13:00–14:00 | Тихий час (сон у базовій кімнаті групи, 1 год) |
| 14:00–15:00 | Вільний час / ігри / прогулянка |
| 15:00–15:30 | Полуденок (30 хв) |
| 15:30–16:30 | Вільний час / збір дітей додому |

### Правила
- **Регулярність:** кожна група має 1 заняття на день (5 занять на тиждень — усі 5 дисциплін). Розклад однаковий за кількістю занять для груп одного віку.
- **Конфлікти:** одна група не може перебувати у двох місцях одночасно; викладач або аудиторія не можуть бути зайняті двома групами одночасно (`409 Conflict`).
- Поки група на занятті у профільного викладача, її вихователь вільний від обов'язків.

### Алгоритм чернетки (`POST /schedules/generate`)
1. Усі групи сортуються за віком від старших (5 років) до молодших (2 роки).
2. Дисципліни мають фіксований порядок (за `id`). Для групи з індексом `i` (`0 ≤ i < N`) у день `d` (0 = Пн, … 4 = Пт) предмет визначається формулою:
   $$\text{activityIndex} = (i + d) \bmod 5$$
3. Групи з однаковим предметом у той самий день отримують послідовні слоти по 30 хвилин, починаючи з 09:30, за спаданням віку (старші йдуть першими).

## 6. Порядок виконання задач (Roadmap)

> **Організація коду:** оскільки весь код пишеться в одному файлі `index.js`, використовуйте коментарі для розділення блоків (`DB Init & Migrations`, `Middleware & Auth`, `CRUD Routes`, `Finance Logic`, `Schedule Logic`). Розрахункові функції пишіть як чисті функції без сайд-ефектів.

3. **Автентифікація:** `POST /auth/login`, перевірка пароля через `bcryptjs`, генерація JWT; мідлвара токена та ролі (`requireRole`); `POST /users` для створення акаунтів (див. розділ 2).
4. **Простий CRUD:** `parents`, `rooms`, `employees`, `activities`. `DELETE` лише для `admin`.
5. **Складний CRUD:** `groups` (макс. 20 дітей, макс. 30 груп), `children` (вік 2–5, правило «один вік у групі», `isActive`); батьки бачать і редагують (лише `notes`) тільки своїх дітей.

### Етап 2: Фінансова логіка (Пріоритет: Високий)

7. **Рахунки:** `GET /children/:id/invoice` (адмін, менеджер, батьки цієї дитини).
8. **Прибуток:** `GET /groups/:id/profit`, `GET /admin/profit` (лише активні діти, лише `admin`).

### Етап 3: Розклад занять (Пріоритет: Середній)
9. Таблиця `schedule_slots` у блоці ініціалізації.
10. Функція перевірки перетинів викладача, кімнати або групи (`409 Conflict`).
11. `GET /groups/:id/schedule`, `GET /teachers/:id/schedule`, `PATCH /schedules/:id` (адмін, менеджер, викладач для своїх слотів).
12. Автогенерація: `POST /schedules/generate` за алгоритмом розділу 5.

### Етап 4: Аналітика та Прогнозування (Пріоритет: Низький / Бонус)
13. `GET /admin/forecast`: симуляція прибутку для заданої кількості дітей без збереження в БД.
14. Оптимізація: порівняння груп по 12 і по 20 дітей, мінімально необхідна кількість спеціалізованих кабінетів та мінімальна окупна кількість кімнат.

Розділи 7–12 це не вимоги замовника, а домовленості й підказки, щоб п'ятеро розробників писали код в одному стилі та не заважали одне одному. Якщо щось не підходить, команда може змінити, але зробіть це спільним рішенням і запишіть тут.

## 7. Технічні домовленості

| Тема | Домовленість |
| --- | --- |
| Назви полів | `camelCase` і в JSON, і в колонках SQLite (без перейменувань між БД і API) |
| Ідентифікатори | цілі числа, `INTEGER PRIMARY KEY AUTOINCREMENT` |
| Дати | рядок `YYYY-MM-DD` (наприклад `2022-03-15`), час `HH:MM` |
| Гроші | цілі числа в гривнях, без копійок і дробових значень |
| Вік | функція `calcAge(birthDate, onDate)`: повні роки на дату; не просто різниця років |
| SQL | лише підготовлені запити `db.prepare(...)` з параметрами `?`, ніколи не склеювати рядок із даних запиту (захист від SQL-ін'єкцій) |
| Зовнішні ключі | на старті виконати `db.pragma('foreign_keys = ON')`, інакше SQLite їх не перевіряє |
| Паролі | зберігати лише `passwordHash` (`bcryptjs`); у відповідях API ніколи не повертати хеш |
| JWT | секрет з `process.env.JWT_SECRET`, термін дії 8 годин; у токені `userId` і `role` |
| Тіло відповіді | один об'єкт або масив у JSON; для `DELETE` статус `204` без тіла |
| Валідація | відсутнє або некоректне поле дає `400` з поясненням у `error` |
| Видалення | якщо запис використовується (кімната в групі, група з дітьми, викладач у слотах), відповідь `409`, а не каскадне видалення |
| Константи | тарифи й ставки вказати одним об'єктом `CONFIG` на початку `index.js`; редагування тарифів через API (`PATCH /settings`) це бонус після етапу 2 |
| Пагінація | не потрібна |

## 8. Модель даних (таблиці SQLite)

| Таблиця | Колонки                                                                                   | Обмеження                                                                                                                                                                                                                                                                                                                             |
| --- |-------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `users` | id, login, passwordHash, role, parentId, employeeId                                       | `login` унікальний; `role` одна з `admin`, `manager`, `parent`, `teacher`                                                                                                                                                                                                                                                             |
| `parents` | id, fullName, phone, email, relationNote                                                  | `relationNote` довільний рядок («родич адміна», «депутат», «знайомий»)                                                                                                                                                                                                                                                                |
| `children` | id, fullName, birthDate, parentId, groupId, discountPercent, paymentPlan, notes, isActive | `discountPercent` у 0, 10, 20, 30; `paymentPlan` у `monthly`, `yearly`; `isActive` за замовчуванням 1                                                                                                                                                                                                                                 |
| `groups` | id, name, ageCategory, capacity, roomId, educatorId, assistantId                          | `ageCategory` від 2 до 5; `roomId` унікальний (одна кімната на одну групу); `capacity` від 1 до 20, за замовчуванням 20                                                                                                                                                                                                               |
| `rooms` | id, name, type, rent                                                                      | `type` у `base`, `specialized`; `rent` за замовчуванням 50000                                                                                                                                                                                                                                                                         |
| `employees` | id, fullName, position, salaryRate                                                        | `position` у `manager`, `educator`, `assistant`, `teacher`; `salaryRate` може бути `NULL` (за замовчуванням `NULL`): для `educator` і `assistant` зарплата рахується динамічно від кількості дітей у групі, для `manager` і `teacher` використовуються ставки з `CONFIG` (80 000 і 40 000), а `salaryRate` лишається довідковим полем |
| `activities` | id, name, teacherId, roomId                                                               | `name` унікальна; `roomId` вказує на спеціалізований зал                                                                                                                                                                                                                                                                              |

Оренда для розрахунку: `SUM(rent)` по таблиці `rooms`. Поки значення не змінювали, вона дорівнює 50 000 × кількість кімнат.

Початкові дані (seed) при першому запуску: користувач `admin`, 5 дисциплін (музика, англійська, фізкультура, вільна боротьба, шахи). Решту даних (діти, групи, викладачі) заводять через API.

## 10. Критерії готовності (Definition of Done)

Задача вважається зробленою, лише якщо виконані всі пункти:

1. Ендпойнт працює з нуля на чистій базі (видаліть `kindergarten.db` і перезапустіть).
2. Повертає правильні статус-коди й формат помилки з розділу 1.
3. Права ролей перевірені: без токена `401`, не та роль `403`, чужі дані недоступні.
4. QA пройшов запити в Postman за таблицею розділу 9 і підтвердив у задачі.
5. Код пройшов review і злитий у `dev` через merge request.

Критерії по етапах:

| Етап | Готово, коли |
| --- | --- |
| 1 | Адмін виконує CRUD над усіма сутностями; батько бачить лише свою дитину; групи не порушують правила віку й місткості |
| 2 | Рахунок збігається з таблицею знижок (наприклад 30% і `yearly` дає 110 880 грн за навчання); прибуток групи з 12 п'ятирічок без пільг на `monthly` дорівнює 86 000 грн |
| 3 | Згенерований розклад без конфліктів, кожна група має 5 занять на тиждень; дублювання слота повертає `409` |
| 4 | Прогноз для 150 дітей по 5 років повертає розрахунок із кількістю груп, викладачів, кімнат і прибутком |

## 12. Запуск і перевірка

### Запуск
1. Встановити Node.js (версія 18 або новіша).
2. У папці проєкту: `npm install`.
3. Створити файл `.env` або задати змінні середовища: `PORT=3000`, `JWT_SECRET=<довільний довгий рядок>`, `ADMIN_PASSWORD=<пароль адміна для seed>`. Секрети не комітити в репозиторій.
4. Запустити: `node index.js`. При першому старті створюються `kindergarten.db`, таблиці й початкові дані.

### Налаштування локального середовища (.env)

Для запуску проєкту кожен учасник команди повинен налаштувати власні змінні середовища.

**1. Встановлення залежностей**

У терміналі WebStorm, перебуваючи в кореневій папці проєкту, виконайте:

```bash
npm ci
```

**2. Створення файлу `.env`**

У кореневій папці проєкту, поряд з `index.js` і `package.json`, створіть файл `.env`.

Додайте до нього:

```dotenv
PORT=3000
ADMIN_PASSWORD=your_generated_password
JWT_SECRET=your_generated_secret
```

Значення `ADMIN_PASSWORD` та `JWT_SECRET` потрібно замінити власними випадково згенерованими значеннями.

**3. Генерація пароля адміністратора**

Виконайте:

```bash
node -e "console.log(require('crypto').randomBytes(18).toString('hex'))"
```

Команда згенерує випадковий пароль із 36 символів. Скопіюйте його у `ADMIN_PASSWORD`.

Пароль повинен містити щонайменше 12 символів.

**4. Генерація JWT_SECRET**

Виконайте:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Команда згенерує випадковий секретний ключ. Вставте його у `JWT_SECRET`.

**5. Запуск проєкту**

```bash
npm run dev
```

Під час першого запуску автоматично створюються:
- Локальна SQLite-база `kindergarten.db`.
- Вісім таблиць бази даних.
- Користувач `admin` із хешованим паролем.
- П'ять початкових дисциплін.

**6. Перевірка працездатності**

Відкрийте в браузері:

`http://localhost:3000/api/health`

Очікувана відповідь:

```json
{
  "status": "ok",
  "database": "connected",
  "message": "Kindergarten API працює"
}
```

**Важливо:**

- Файл `.env` не завантажується на GitHub, оскільки він доданий до `.gitignore`.
- Кожен розробник використовує власні паролі та локальну базу даних.
- Не передавайте `ADMIN_PASSWORD` та `JWT_SECRET` іншим учасникам.
- Зміна `ADMIN_PASSWORD` у `.env` не змінює пароль уже створеного адміністратора.
- Для повторного створення тестової бази можна зупинити сервер, видалити `kindergarten.db` і запустити його знову. Усі локальні записи при цьому будуть втрачені.
- Функціонал входу через `POST /auth/login` стане доступним після реалізації модуля авторизації.

### Перший тест
1. Вхід: `POST /auth/login` з тілом `{ "login": "admin", "password": "<ADMIN_PASSWORD>" }`, у відповіді токен.
2. Усі інші запити з заголовком `Authorization: Bearer <токен>`.
3. Створіть батька, групу, дитину, перевірте `GET /children/:id/invoice` і порівняйте суму з таблицею знижок у розділі 4.

### Типові помилки новачків
- Забули `foreign_keys = ON`, тому «неіснуючі» зв'язки проходять без помилок.
- Рахують вік як різницю років без урахування місяця й дня.
- Склеюють SQL з даних запиту замість підготовлених запитів.
- Повертають у відповіді `passwordHash`.
- Плутають `401` (немає або невалідний токен) і `403` (токен є, але прав недостатньо).
- Перевіряють роль, але не перевіряють, чия це дитина чи слот.
- Пишуть одну величезну функцію на весь ендпойнт замість маленьких окремих.
- Пушать у `dev` не перевірене QA.
