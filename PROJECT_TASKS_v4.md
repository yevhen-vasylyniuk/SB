## 3. Опис змін і критерії приймання

### 3.1. Права на `salaryRate` — Василинюк Євген

- `POST /employees` і `PATCH /employees/:id`: менеджер із полем `salaryRate` отримує `403` (`Object.hasOwn(req.body, 'salaryRate')`), так само як для `rent`.
- Менеджер без `salaryRate` створює й змінює працівників без обмежень, адміністратор може встановлювати й змінювати ставку.
- Перевірка стоїть до будь-яких записів у БД, тому після `403` нічого не змінюється й історія змін не засмічується.
- Тести: `test/manager_salary_rate.test.js`; документація оновлена.
- **Нюанс порядку перевірок:** валідація тіла передує перевірці ролі, тому некоректне значення `salaryRate` може повернути `400` замість `403`.

### 3.2. Генератор розкладу — Василинюк Євген

- Порядок груп: від старших, `ageCategory DESC, id`; дисципліна групи `i` у день `d` — `activities[(i + d) mod 5]` (формула з ТЗ).
- `buildWeeklySchedule` ставить кожне заняття в перший вільний слот 09:30–12:00 (шість слотів), де вільні група, викладач і зал. Дисципліни можуть ділити зал або викладача.
- Якщо кожна дисципліна має свій зал і викладача, розклад збігається з колишнім.
- Замість помилки SQLite `UNIQUE` повертається `409` з поясненням (день, група, зал або викладач, кількість занять, мінімум залів); `409` також без жодної групи. Старий розклад видаляється лише після успішної побудови нового.
- Сітка слотів — константа `SCHEDULE_SLOT_TIMES`, її використовує й `PATCH /schedules/:id`.
- Тести: `test/schedule_generate.test.js`; оновлено README (розділ 5), API-документацію (5.9) і критерії приймання.

### 3.3. Форекаст розкладу — Вацко Петро, Василинюк Євген

- До `GET /admin/forecast` додано блок `optimization`: `minSpecializedRooms`, `minTotalRooms`, `netProfitWithMinRooms`, `breakEvenRooms` (мінімальна окупна кількість груп і кімнат, або `null`). Старі поля відповіді не змінені.
- Початкова формула `ceil(груп / 6)` давала занижений мінімум для 11–12 і 16–24 груп. Євген замінив її розрахунком за правилами генератора (перебір 52 способів розподілити п'ять дисциплін по залах, до 6 занять на зал на день). Результат: 11–12 груп → 3 зали, 16–24 → 5; для 6–10 і 30 груп значення не змінилися.
- Підказка «щонайменше N залів» у `409` генератора використовує ту саму функцію, тому числа завжди збігаються.
- Тести: `test/forecast_rooms.test.js` (6, 7, 8, 10–13, 16, 24, 30 груп) і тест для 11 груп у `schedule_generate.test.js`.

### 3.4. Робота за назвою — Сосновець Дмитро

- `GET /activities?name=` — пошук за частиною назви без урахування регістру; без `name` повертає всі дисципліни, порожній результат — `200` і `[]`.
- `GET`, `PATCH`, `DELETE /activities/by-name/:name` — операції за точною назвою; маршрути з `id` збережені й використовують ті самі обробники.
- Назва дисципліни унікальна; спроба створити чи перейменувати на існуючу → `409`; неіснуюча назва → `404`; некоректна → `400`.
- Права ролей не змінені (DELETE лише `admin`).
- Тести: `test/activities_by_name.test.js`; документація оновлена.
- **Обсяг:** реалізовано лише для дисциплін; групи, кімнати й працівники залишилися з `id`.

### 3.5. Розклад викладача і сортування — Угринюк Микола

- `GET /teachers/:id/schedule` для викладача без занять повертає `200` і `[]` (раніше `404`); для неіснуючого викладача `404` зберігається.
- Генератор розкладу сортує групи за `ageCategory DESC, id`, тож порядок груп однієї вікової категорії стабільний.
- Видалено сміттєвий коментар `// dimadiamdimma`.
- **Не змінено:** `GET /groups/:id/schedule` для групи без занять досі повертає `404`.

## 5. Командні правила

- Нові зміни — в окремих `feature/*` або `fix/*` гілках, Pull Request у `dev`, без прямого запису в `main`.
- PR не зливаємо без рев'ю: один автор, один рецензент, коментар із результатом перевірки.
- Погоджувати зміни в одному `index.js`, особливо якщо кілька учасників змінюють ті самі маршрути; PR з форматуванням (Prettier) зливається останнім.
- Для кожної задачі: опис зміни, потрібні права, позитивні й негативні тести й результат QA.
- Документація: `README.md` — вимоги й ролі; `docs/` — API та критерії приймання; `PROJECT_TASKS_v4.md` — цей звіт; попередні звіти залишаються окремими файлами.
