# SB — REST API для приватного дитячого садка

**Дата оновлення:** 18.10.2026

## 1. Мета проєкту

Створити REST API для управління приватним дитячим садком. Повні вимоги, модель даних, фінансові правила, розклад і таблиця ендпойнтів описані в `README.md` (це технічне завдання). Цей файл описує, **хто і що робить**.

## 2. Обов'язкове технічне обмеження

**Увесь програмний код проєкту має бути в одному файлі `index.js`.**

У `index.js` розміщуються:
- налаштування Express;
- підключення та налаштування SQLite;
- створення таблиць і початкових даних;
- реєстрація та авторизація;
- JWT і middleware перевірки ролей;
- усі маршрути API;
- бізнес-логіка;
- перевірка вхідних даних;
- обробка помилок;
- запуск сервера.

Не створювати окремі файли `auth.js`, `database.js`, `routes.js`, `controllers.js`, `models.js` або інші файли з програмною логікою.

Допоміжні файли дозволені: `package.json`, `package-lock.json`, `.gitignore`, `README.md`, документація та файл змінних середовища `.env` (секрети не завантажувати на GitHub).

## 3. Технології

- Node.js
- Express
- SQLite через `better-sqlite3`
- `bcryptjs` для хешування паролів
- `jsonwebtoken` для JWT
- `dotenv` для конфігурації

### Громов Олександр — Dev (кімнати, заняття)
- CRUD для `rooms` і `activities`; `DELETE` лише для `admin`, відповідь `409`, якщо запис використовується.
- Функція `findScheduleConflict(slot, ignoreId = null)` для перевірки перетинів розкладу. **Від неї залежить Стасів** (`PATCH /schedules/:id`, `POST /schedules/generate`), тому сигнатуру не змінювати без домовленості з ним. Контракт нижче. Функцію пишеш ти в блоці кімнат і занять; Стасів у своїй гілці має тимчасову заглушку з таким самим іменем (`return null`), яку прибирають під час злиття.

**Контракт `findScheduleConflict(slot, ignoreId = null)`**

| | |
|---|---|
| Приймає `slot` | об'єкт `{ groupId, teacherId, roomId, dayOfWeek, startTime, durationMin }`: `dayOfWeek` число 0–4, `startTime` рядок `"HH:MM"` (наприклад `"09:30"`), `durationMin` завжди 30. Значення вже перевірені маршрутом (діапазони, час на сітці 09:30–12:00 з кроком 30 хв), функція їх не валідує. |
| Приймає `ignoreId` | число або `null`: `id` слота, який зараз редагується, його треба виключити з пошуку. Для створення нового слота (генератор) `null`. |
| Читає | таблицю `schedule_slots`, **нічого не пише**. Лише підготовлені запити `db.prepare(...)` з `?`. |
| Логіка | шукає записи з тим самим `dayOfWeek` і `startTime` (усі слоти по 30 хв на одній сітці, тож збіг початку це перетин), крім слота з `ignoreId`. Колізія, якщо збігається `groupId`, `teacherId` або `roomId`. Перевіряти в такому порядку: група, викладач, кімната; повернути перший знайдений. |
| Повертає | `null`, якщо накладок немає. Інакше об'єкт `{ type, slotId }`, де `type` це `'group_busy'`, `'teacher_busy'` або `'room_busy'`, а `slotId` це `id` слота, з яким колізія. |

Важливо:
- Виключення поточного слота писати як `WHERE id IS NOT ?`, а **не** `id != ?`. Для `ignoreId = null` вираз `id != NULL` не дає жодного рядка, і колізії не знайдуться.
- Маршрут Стасіва при непорожній відповіді повертає `409` у форматі ТЗ: `{ "error": "опис", "type": ..., "slotId": ... }`.
- Окрім цієї перевірки, у таблиці є `UNIQUE` на (група, день, час), (викладач, день, час), (кімната, день, час). Якщо хтось обійде функцію, БД теж відхилить запис, і `SQLITE_CONSTRAINT_UNIQUE` теж має давати `409`.
- Тест: два слоти в одну годину з одним викладачем дають `{ type: 'teacher_busy', slotId }`; той самий слот, що редагується, колізії з самим собою не дає.

### Вацко Петро — Dev (фінанси)
- Чисті функції без доступу до БД: `calcTuition`, `calcMeals`, `calcEducatorSalary`, `calcAssistantSalary`. Контракт нижче; **від нього залежить Стасів** (прибуток), тому сигнатури не змінювати без домовленості з ним.
- Усі суми це цілі гривні без копійок. Константи (15 000, 12%, тарифи харчування, 20 робочих днів, 80 000, 40 000, 50 000) винести в об'єкт `CONFIG` на початку `index.js`. Функції пишуться в блоці «РАХУНКИ» як `function`, щоб інші могли їх викликати.
- Після merge дітей і груп: `GET /children/:id/invoice`. Рахунок рахується «на льоту», окремих таблиць рахунків і платежів немає.

**Контракт функцій**

| Функція | Приймає | Повертає |
|---|---|---|
| `calcTuition(child)` | `child = { discountPercent, paymentPlan }`, де `discountPercent` це 0, 10, 20 або 30, а `paymentPlan` це `'monthly'` або `'yearly'` | `{ perMonth, perYear }` |
| `calcMeals(age)` | вік 2, 3, 4 або 5 (число). Вік визначає той, хто викликає: `group.ageCategory`, а без групи повний вік за `birthDate` | `{ perDay, perMonth, perYear }` |
| `calcEducatorSalary(kidsCount)` | кількість **активних** дітей у групі, ціле 0–20 | зарплата вихователя за місяць (число) |
| `calcAssistantSalary(kidsCount)` | те саме | зарплата помічника за місяць (число) |

Формули:
- `calcTuition`: `річна база = 180 000 × (100 − discountPercent) / 100`. План `monthly`: `perYear` = ця сума, `perMonth` = `perYear / 12`. План `yearly`: `perYear` = `річна база × 88 / 100`, `perMonth` = `perYear / 12`. Тобто `perMonth` це **місячний еквівалент**, саме він іде в розрахунок прибутку. Результат округлювати `Math.round`.
- `calcMeals`: `perDay` = 300, 400, 500 або 600 за віком 2, 3, 4, 5; `perMonth` = `perDay × 20`; `perYear` = `perMonth × 12`. Пільги на харчування не діють, у прибуток садка харчування не входить.
- `calcEducatorSalary`: `2 000 × min(n, 12) + 5 000 × max(0, n − 12)`.
- `calcAssistantSalary`: `20 000 + 3 000 × max(0, n − 12)`.
- Некоректний вхід (вік поза 2–5, `kidsCount` поза 0–20, невідомий план чи пільга): `throw new RangeError(...)`. Маршрути перевіряють дані до виклику, тому функція не повертає `NaN` і не мовчить.

Контрольні значення (перевірити перед PR):

| Виклик | Результат |
|---|---|
| `calcTuition({ discountPercent: 0, paymentPlan: 'monthly' })` | `{ perMonth: 15000, perYear: 180000 }` |
| `calcTuition({ discountPercent: 10, paymentPlan: 'yearly' })` | `{ perMonth: 11880, perYear: 142560 }` |
| `calcTuition({ discountPercent: 30, paymentPlan: 'monthly' })` | `{ perMonth: 10500, perYear: 126000 }` |
| `calcTuition({ discountPercent: 30, paymentPlan: 'yearly' })` | `{ perMonth: 9240, perYear: 110880 }` |
| `calcMeals(3)` | `{ perDay: 400, perMonth: 8000, perYear: 96000 }` |
| `calcEducatorSalary(15)` / `calcEducatorSalary(20)` | 39 000 / 64 000 |
| `calcAssistantSalary(15)` / `calcAssistantSalary(20)` | 29 000 / 44 000 |
| прибуток групи: 12 п'ятирічок, без пільг, `monthly` | 86 000 (180 000 − 50 000 − 24 000 − 20 000) |

Підсумок рахунку `GET /children/:id/invoice` (рядки «Навчання», «Харчування», «Підсумок»): `monthly` це `perMonth` навчання + `meals.perMonth`; `yearly` це `perYear` навчання + `meals.perYear`. Для неактивної дитини `409`.

## 7. Критерії готовності функції

Функція вважається готовою, коли:
- реалізація відповідає погодженим вимогам (ТЗ);
- перевіряються обов'язкові поля та некоректні дані (`400`);
- налаштовані потрібні права доступу (`401`, `403`);
- повертаються відповідні HTTP-статуси і формат помилки `{ "error": "опис" }`;
- обробляються очікувані помилки (`404`, `409`);
- функція працює на чистій базі (видалити `kindergarten.db` і перезапустити);
- функцію перевірено тестовими запитами, QA підтвердив;
- код пройшов review і інтегрований у `dev` через PR без порушення роботи інших функцій.
